## 3. 核心机制详解

### 3.1 多 Tab + 保活（alive）

**关键约束**：无界保活模式（`alive: true`）下，**同一个 `name` 改 `url` 无法跳转不同路由**。

因此本项目的模型是：

- **每个 tab = 一个独立的无界实例**，实例名唯一：`name = ${appName}-${tabId}`
- **`appName`** 单独作为"逻辑子应用"字段，用于分组统计（如"审批中心还开着几个 tab"）
- 这样同一个子应用可以开多个菜单项（不同内部路由）的 tab，各自独立、互不干扰

**保活的实现方式**：每个 tab 有自己的容器 `div`（常驻 DOM），用 `v-show` 切换显隐。切走的 tab 容器只是 `display:none`，无界实例仍在容器里活着，切回来不重新加载。

> 文件名带注释：`packages/tab-manager/src/TabManager.ts` 类头部有详细说明。

### 3.2 空闲超时自动销毁

- 每个实例有一个**空闲定时器**，默认 **10 分钟**（可用 `VITE_TAB_IDLE_TIMEOUT` 覆盖）
- **激活某个 tab 时**：清除该实例定时器、给上一个激活的 tab 启动定时器
- **定时器触发**：调用 `destroyApp(name)` 销毁实例，状态标记为 `destroyed`；**tab 标签保留**
- **点击已销毁的 tab**：状态是 `destroyed` → 触发 `mountTab` 重新加载

实测结论：重载时**入口 HTML 不会重新请求**（无界内部缓存了），但**子应用 JS 模块会全部重新拉取执行**，页面状态被重置 —— 属于真正的重新加载。

### 3.3 Tab 持久化与刷新恢复

- 打开的 tab 元数据（`id/appName/name/title/url/route`）持久化到 **sessionStorage**（key: `platform-tabs`）
- 刷新后：**完整还原 tab 栏**，但**只挂载当前激活的那个**，其余懒加载（点到才 `startApp`）
- 实测：刷新前已挂载 2/2 → 刷新后已挂载 1/2 ✅

### 3.4 主题同步链路

```
主应用点击切换
  → themeStore.setMode()
      ├─ applyTheme()           在 <html> 上设 data-theme="light|dark"
      ├─ storeTheme()           写入 localStorage（刷新/子应用首屏恢复）
      └─ bus.$emit(THEME_CHANGE) ────┐
                                     ▼
子应用 initTheme() 监听 bus → applyTheme() 切换自己的 data-theme
```

**为什么子应用要各自引一份 `theme.css`**：无界是 iframe 隔离，主应用 `:root` 的 CSS 变量**不会穿透**到子应用，所以两边各自引用同一份变量文件来保证品牌统一。

实测：主应用 light→dark，子应用 shadow DOM 内的 `<html data-theme>` 同步变为 dark ✅

### 3.5 跨应用桥（token / 用户信息）

主应用把读取函数挂在 `window.__PLATFORM__` 上（见 `apps/main/src/wujie/index.ts`）：

```ts
window.__PLATFORM__ = {
  getToken: () => userStore.token || null,
  getUser:  () => userStore.userInfo,
  getTheme: () => themeStore.mode,
};
```

子应用（同域 iframe）通过 `window.parent.__PLATFORM__.getToken()` **实时**读取。

**为什么不用 props**：props 是 `startApp` 时的一次性快照，token 刷新后子应用拿到的是旧值，会导致请求带过期 token。所以：

| 数据 | 传递方式 |
|---|---|
| 用户信息（静态展示用） | `props` 快照下发 |
| token / 主题等**会变**的数据 | 跨应用桥 / bus **实时**获取 |

## 4. 关键设计决策与踩坑记录

### ★ 踩坑 1：子应用完全挂不上（已修）

**现象**：点菜单后 tab 标签出来了，但内容区一片空白，**F12 控制台没有任何报错**。

**根因**：`TabManager.mountTab` 里的幂等守卫与"新建记录的初始状态"冲突：

```ts
// getOrCreateRecord 新建记录时 status 是 'loading'
if (record.status === 'loading' || record.status === 'loaded') return;  // ← 首次就死在这里
```

新建记录的初始状态恰好是 `'loading'`，导致**首次挂载必然被自己拦掉，`startApp` 一次都没执行过**。因为什么都没做错，所以没有任何报错。

**修复**：新增 `'idle'` 状态作为新建记录的初始态（`types.ts` + `TabManager.ts`）。

**排查手法**（值得复用）：用**无头 Chrome + 原生 CDP**（Node 自带 `WebSocket`，零依赖）实际打开页面、点菜单，抓控制台/网络/DOM。决定性证据是：**发往子应用端口的请求数为 0** —— 直接锁定"根本没调用 startApp"。

### ★ 踩坑 2：误判为"Vite dev 不支持无界默认模式"

一度以为 Vite dev 的 ES Module 与无界默认沙箱不兼容，加了 `degrade: true`（降级 iframe）。

后来做**对照实验**证明是误判：把 `degrade` 设回 `false` 后，默认模式在 Vite dev 下**完全正常**，无界会自动处理（shadow DOM 里能看到 `<!-- script http://localhost:5174/@vite/client replaced by wujie -->`）。

**结论**：`degrade` 相关改动已全部撤销，项目走**无界默认 iframe 隔离**，生产代码路径干净。

### 设计决策 1：tab 模型用"唯一 name + appName 分组"

原因见 3.1 —— 保活模式下同名实例无法改路由，这是被官方文档明确警告的限制。

### 设计决策 2：每个 tab 一个常驻容器 + `v-show` 切换

不依赖无界内部的 webcomponent 热插拔，行为更可预测（`DefaultLayout.vue`）。

### 设计决策 3：`degrade` 保留为可选项但默认关闭

`TabManager` 保留了 `degrade` 选项（无界原生能力），遇到特定浏览器兼容问题时可开启，但默认 `false`。

## 8. 接入一个新子应用

1. 复制 `templates/sub-app/` 到 `apps/` 下并重命名（如 `apps/inventory`）
2. 改 `package.json` 的 `name`（如 `@platform/inventory`）
3. 改 `vite.config.ts` 的端口（主应用 5173、审批 5174，新子应用顺延 **5175、5176…**）
4. 改 `index.html` 的 `<title>`
5. 在 `src/router/index.ts` 定义本子应用路由
6. 在主应用 `apps/main/src/config/menu.ts` 里：
   - `appRegistry` 注册 base url（生产环境填 nginx/CDN 地址）
   - `menus` 加菜单项（`title` / `appName` / `route`）

### 子应用必须遵守的约定

- 引入 `@platform/ui-theme/theme.css`，样式一律用 CSS 变量，**不要写死颜色**
- 请求走 `@platform/sdk`，token 从 `window.parent.__PLATFORM__.getToken()` 实时取，**禁止自存 token**
- 优先使用 `@platform/ui-components` 的封装组件
- 用户信息从 `window.$wujie.props.user` 读取（快照）
- 实现 `__WUJIE_MOUNT` / `__WUJIE_UNMOUNT` 生命周期
